MACHINE OVERVIEW HELP

Purpose

Machine Overview provides a lightweight, always-available view of current Windows machine health. It combines CPU, memory, GPU, responsiveness, disk, application, and incident signals so we can see likely pressure without opening several diagnostic tools.

Its purpose is triage, not exact root-cause analysis. Lightweight counters have limitations: they can show that a stall, queue, interrupt, or DPC load is suspicious, but they cannot always identify the responsible driver or operation. Missing providers are reported as unavailable rather than treated as machine failure. False positives remain possible when a short workload crosses an automatic incident threshold.

Sampling and display refresh

Collection and display refresh run at different frequencies. System samples are normally collected every 1 second, process samples every 5 seconds, and optional temperature samples every 3 seconds. The panel normally replaces its visible snapshot every 10 seconds. History commits are batched at roughly 10-second intervals, so no synchronous disk write occurs for every sample.

Changing DisplayRefreshIntervalMs changes only how often the panel renders the newest immutable snapshot. It does not change collection frequency. Display refresh is clamped to 2 through 60 seconds.

Controls and shortcuts

F8 focuses the Machine Overview row list.

Ctrl+E toggles Freeze display and Resume display. Freeze holds the visible rows only. Sampling, aggregation, incident detection, and history continue. Resume jumps directly to the newest snapshot.

Shift+F8 toggles Full View and Restore View. Full View hides the other panels and splitters and gives the client area to Machine Overview. Restore View returns their exact prior visibility and widths. Full View is not saved across restart.

Alt+H or the Help button opens this dialog. The help text is selectable. Ctrl+C copies the selected help text, Escape closes the dialog, and Tab moves between the text and Close button.

Up and Down move through rows. Enter on the Incidents row opens incident history. Enter on other rows has no special action.

Ctrl+C in the Machine Overview panel copies the selected row's complete label and value, including text clipped on screen. Ctrl+Shift+C copies a timestamped full diagnostic snapshot with all rows, complete ranked-application PID lists, provider state and age, provider collection latency, logical-processor values, queue and drop counters, SQLite status, monitor overhead, incidents, and application path status.

Time values

Now is the newest accepted sample. Average is the arithmetic average over the named covered window. Peak is the highest one-second sample in that window. CPU and GPU summaries use 5, 15, and 60 seconds. A value is marked stale when its provider has not supplied a sufficiently recent sample or rolling-window coverage is below 80 percent. A value is unavailable when the provider, permission, counter, or hardware support is absent.

CPU

Total CPU is normalized to the whole machine and remains between 0 and 100 percent. Each process is normalized to the whole machine before matching executable names are summed for the application rankings. A hot logical processor is one whose covered 5-second average is at least 80 percent. The row reports the current total, hot logical processors, averages, one-second peaks, and package temperature when an optional provider is available.

Memory

Physical memory is installed RAM currently in use. Available memory is RAM Windows can provide without first paging occupied data. Commit is virtual memory committed against RAM and page files. Paging is the current and peak transfer rate caused by paging activity. Application RAM ranking sums the private working sets of processes with the same executable name.

GPU

GPU engine load is the busiest WDDM engine percentage, not a sum of engines that could exceed 100 percent. The row includes now, 5/15/60-second average and peak values, dedicated memory use, and provider age. GPU temperature and power are optional. Provider availability is explicit when WDDM, NVIDIA, temperature, or permission support is missing.

Disks and volumes

Disk active time is the percentage of time a physical disk is servicing requests. Throughput is read and write MB/s. Latency is request time in milliseconds. Queue length is outstanding work. The disk summary chooses the worst current physical disk using latency, queue length, active time, and supporting throughput instead of calling high throughput unhealthy by itself. Each physical-disk row also reports capacity for every mapped volume, including volumes without drive letters when Windows exposes them.

Responsiveness

Foreground reply time is the bounded response time of the current foreground window. A timeout is reported without blocking ActiveAppView. DPC and interrupts are processor time spent servicing deferred procedure calls and hardware interrupts. DWM missed frames indicate desktop-composition delivery gaps. Processor queue is work waiting for CPU service. These signals provide context; they do not by themselves name the faulty driver or application.

Application rankings

The five CPU, RAM, and I/O ranks group processes case-insensitively by executable name. CPU is aggregate whole-machine percent now, 15-second average, and 60-second peak. RAM is aggregate private working set and its recent peak. I/O is aggregate combined read/write MB/s now, 15-second average, and 60-second peak. A row lists up to five numerically sorted member PIDs and adds `(<count> more)` when needed. Ctrl+Shift+C diagnostics include every member PID. Executable paths are best effort and use least-privilege process access; a denied or unavailable path is omitted from the visible row and recorded as path status in the diagnostic copy.

Incidents

Automatic incident detection uses named thresholds, hysteresis, and recovery periods so one sustained condition creates one incident. Severity words appear in text and are not conveyed by color alone. Incidents retain UTC and local start, peak and end times, the threshold explanation, provider freshness, and measured CPU evidence for up to 5 minutes before, the incident itself, and 10 minutes after. Evidence can be collecting, complete, incomplete, removed by the storage budget, or not recorded for an older incident. An incident interrupted by an application restart does not have a recorded end time.

Hot logical processors must remain hot for 30 seconds before an incident starts. The count is 12.5% of the machine's logical processors, rounded up, with a minimum of two: four on a 32-processor machine and two on an 8-processor machine. Hot means the five-second average is at least 80% with sufficient sample coverage. Total CPU at or above 90% suppresses this rule so High CPU owns full-machine saturation. Recovery takes 10 seconds below the required hot count, or at High CPU level. High CPU keeps its existing 90% activation for 15 seconds and 75% recovery for 10 seconds.

Memory pressure starts after five seconds at 95% physical memory use, or at least 100 MB/s paging while physical memory use is at least 90%. Paging at lower physical use does not count as memory pressure. Recovery takes five seconds strictly below 90% physical use. Exactly 90% can activate paging pressure and does not recover an active incident. These incident thresholds are fixed defaults; there are no INI threshold settings.

History schema v4 records per-logical-processor CPU, paging bytes per second and physical memory use. Older rows keep missing values as unavailable. For read-only threshold comparison, run ActiveAppView.exe --replay-machine-overview-incidents=<database path>. Replay requires schema v4 and fresh recording; older rows cannot reconstruct missing signals. It reads up to 10,000 rows per short transaction and reports legacy and tuned incident counts plus whether High CPU starts and ends match. It does not upgrade or write the database. An operational comparison needs at least 24 hours of new v4 recording.

The Incidents row shows the last-24-hour count and the three newest summaries. Enter opens the history view. Its filters are Last 24 hours, Last 7 days, and All, ordered newest first. Select an incident to load its measured evidence without moving selection or focus. The evidence list shows system CPU, DPC and interrupt time, individual processes identified by PID and creation time, application groups, sample coverage and gaps for each phase. Exited processes remain in the evidence. Copy evidence copies the details, recording health and raw database reference as text, including local timezone and UTC times. Freeze display does not freeze incident detection or history.

Process CPU is kernel plus user time divided by the sampling interval and the number of logical processors. On a 32-logical-processor machine, one fully busy logical processor is 3.125% of the whole machine. Measured processes is the total CPU measured across processes; Not attributed is system CPU minus that measured total, clamped to zero. DPC/interrupt time, inaccessible processes, missed samples and processes that start and exit between samples can leave CPU unattributed. Application evidence combines matching executable names from the five busiest groups per sample, so it can understate a group total. These measurements describe contributors, not proof of the cause of an incident.

Memory-pressure evidence adds physical use, commit, paging, and the largest private-byte process contributors. RAM evidence uses private bytes, distinct from the live ranking's private working set. Growth is the last minus the first value seen in each phase. Disk-pressure evidence adds busiest-disk active time, latency, queue and throughput plus process read+write I/O. User-marked incidents retain both RAM and I/O. The recorder reuses the existing samples and keeps up to ten During and five Before/After identities per resource, shortened when necessary to fit the 16 KiB evidence limit. CPU-only incidents keep the original evidence format; older evidence remains readable.

Process I/O counters include file, network and device I/O. Paging and memory-mapped file reads are not attributed to processes. Lists come from the ten largest processes per sample, so absence from a list does not prove a process used no RAM or I/O. RAM averages include only appearances in the list; I/O averages count absent samples as zero over measured phase time. These are measured contributors, not proof of cause.

History and storage

HistoryEnabled controls persistence. One-second system and disk samples are retained for up to 48 hours, 10-second rollups for 30 days, and one-minute rollups for 365 days. Incidents are retained for up to 365 days and at most 50,000 headlines. Ranked application snapshots and compact measured incident evidence share the same storage budget; the full process list is not written every second.

MaxDatabaseSizeMB defaults to 2,048 MiB and is clamped to 256-65,536 MiB. The budget counts used database pages, including incident headlines and evidence. Maintenance trims older data in bounded batches, protects the current write batch and collecting evidence, and normally preserves recent data first. Evidence can be removed before its headline; the history view states when that happens. Trimming continues across commits toward 90% of the budget. Storage states and errors report when trimming is in progress or protected recent data prevents the budget from being met.

The physical database file can stay larger than its used-page budget because SQLite reuses freed pages. The WAL is separate from that budget, with a 64 MiB journal-size limit after checkpoints. Leave additional space for backup and compaction. Before an older database is migrated, ActiveAppView creates a timestamped MachineOverviewHistory.db.pre-migration-v<version>-<timestamp>.bak beside it and verifies its size and incident count. The backup protects the migration and remains if migration fails or is interrupted. After the schema upgrade and legacy cleanup succeed and compaction is completed or deferred, ActiveAppView deletes its recorded backup and backup sidecars, including after a resumed migration. It preserves other backup files. A deletion failure is reported in recording health and diagnostics, keeps the backup path for a later retry, and does not stop recording. Migration requires free space for the main file, WAL and 256 MiB headroom. If space is insufficient, history recording pauses with a MigrationBlocked message while live monitoring continues. Older context is cleared from the database; the incident headlines remain.

Startup may compact the database once when reclaimable space exceeds the larger of 256 MiB or one quarter of the budget and both the database and TEMP drives have enough free space. There is no periodic VACUUM during normal monitoring.

The history database is MachineOverviewHistory.db next to ActiveAppView.exe. It uses the packaged Win64 SQLite 3.53.4 runtime, one background writer, WAL mode, synchronous=NORMAL, prepared batched transactions, bounded retry/backlog behavior, and small retention batches. If the database is busy, corrupt, or unavailable, live monitoring continues and the diagnostics report the failure.

Recording health reports Recording, Stale, Unavailable or Error, with the recording session start, last successful write, newest process sample, retained time range, used bytes and budget, main-file and WAL sizes, storage state, records dropped during the current session, sampling intervals, logical-processor count, provider status, and database/backup paths. A last write older than three commit intervals is stale. A byte budget does not guarantee a fixed number of hours of coverage.

DetailedTraceEnabled is off by default. When enabled without onset tracing, a DPC/ISR incident or a critical automatic incident can request one 15-second WPR trace after detection. ActiveAppView combines the Windows General and GPU profiles so the trace contains CPU scheduling, context switches, DPC/ISR, disk, process/thread, and supported GPU events and stacks. Windows must grant the Profile system performance right; otherwise the incident records Trace: Unavailable without requiring ActiveAppView to elevate. WPA-compatible ETL files are saved under the MachineOverviewTraces directory next to ActiveAppView.exe. They can contain sensitive system activity. Retention keeps at most 10 ETL traces and 2 GB total, deleting the oldest trace files first.

OnsetTraceEnabled=1 replaces that after-detection mode with a continuously recording CPU trace in circular memory. It is off by default and only works when ActiveAppView is already running as administrator; it never asks for elevation. OnsetTraceBufferMB defaults to 256 MB of nonpaged memory while recording and is clamped to 64-1024 MB. Malformed settings use the defaults. The buffer bounds bytes, not time: coverage depends on activity. A user mark, High CPU, DPC/ISR, or critical foreground-response incident saves the ring and restarts it. Automatic saves have a 15-minute cooldown; user marks bypass it. Incidents during saving report that recording was restarting. Saving needs twice the buffer size plus 1 GiB free space. The health block shows recording, waiting, permission, and failure states; each incident shows the saved event span, whether onset is included, and events/buffers lost. Unreadable traces are reported as failed rather than claiming coverage.

Onset ETLs contain process command lines, image paths, and CPU stacks from all processes. They are stored in MachineOverviewTraces next to ActiveAppView.exe with the same 10-file, 2-GB retention. ActiveAppView uses its own WPR instance and waits while another WPR recording is active. The instance name ActiveAppViewOnset is reserved exclusively for ActiveAppView. Other tools must not use that name: a foreign session created between our absence check and start could be cancelled during later cleanup. Recordings with other instance names are left untouched. Closing the app cancels its own ring and releases its memory. Before starting, ActiveAppView checks its instance name and leaves an existing unmarked recording untouched. A flushed marker records Pending or Owned state, creation time, and whether a session existed before the marker. Uncertain starts and cleanup failures retain the marker for automatic retries with bounded backoff; cleanup continues at startup, on the retry timer, and at shutdown even with OnsetTraceEnabled=0. A retained marker shows a possible retained-memory diagnostic; a non-elevated run reports it without requesting elevation. Only a marked session that did not predate its marker can be stopped or cancelled. Failed or unreadable ETL saves still trigger retention. A retention failure is reported alongside the save or inspection error.

Disk evidence names the selected busiest disk for each phase, or Multiple busiest disks when selection varied. Each peak names the disk that produced it. Samples outside the evidence window cannot change these names.

Windows performance recordings

Select an incident, then Read recording to open one or more closed .blg files. The independent Windows recording is a cross-check; ActiveAppView's retained incident evidence remains the primary source. During covers incident start to end, Before the preceding five minutes, and After the following ten minutes. An ongoing incident uses its peak time as the end. Results appear below the retained evidence and in Copy evidence, with local UTC offsets and authoritative Z timestamps. Results are not saved and clear when another incident is selected. Focus and selection stay where we left them when reading finishes. Cancel reading stops the request.

Only closed, user-selected recordings are read, without changing them. ActiveAppView never starts, stops, copies, configures, or otherwise controls the collector. A file named current.blg is refused before opening it. This is the collector's active circular log; Windows cannot read it while recording, including a byte copy made while it is open. Preserve it with the elevated stop/copy/restart runbook in PC-Maintenance docs\performance-recording.md, then open the preserved copy. ActiveAppView does not perform those steps. previous.blg covers only the session before the last collector restart; for most incidents a readable recording exists only after preservation.

Counter names are resolved through Windows by index, including on Polish Windows. Process CPU is percent of the whole machine, divided by the incident's logical-processor count, falling back to this computer's count. One fully busy LP on a 32-LP machine is 3.125% of machine. A recording from another computer warns us to verify that count. Process identity combines PID with creation time inferred from elapsed time, with precision of approximately one recording interval. Instance renumbering does not change identity; PID reuse with a new elapsed time creates another identity. Idle and _Total process instances are excluded. Exited processes remain listed; absence contributes zero over valid sample time. The list shows the 10 busiest During processes and 5 Before and After, with average, peak, peak time, sample count and last seen. CPU lists are measurements, not proof of cause.

The result reports the log range, full/partial/no coverage, uncovered ranges, sampling interval, invalid values, normalization and file names. Invalid first samples and missing values are excluded. Log timestamps are local Windows FILETIMEs converted with this computer's time-zone rules; the repeated hour at the DST fall-back is ambiguous. Reading runs off the UI thread, checks cancellation between PDH operations and samples, and shows a timed-out state after 120 seconds, discarding late results. Closing the history window signals cancellation and returns immediately. Individual Windows PDH calls cannot be interrupted; the detached reader owns its handles and cleans up when storage responds. At application exit, readers have a 250 ms cleanup grace period; if still blocked, Windows terminates this process before unit finalization and reclaims its private resources. Up to four unfinished recording readers are allowed across windows; further reads report busy until one finishes. Limits are 32 selected files, 2 GB combined, 8,192 process instances, 65,536 process identities and an 8-million-character counter catalogue; errors and truncation are shown.

Privacy and information not stored

Normal Machine Overview history does not store window titles, command-line arguments, typed text, clipboard contents, or keystrokes. It may store executable name, member PIDs, process creation times, best-effort executable path, ranked values, measured incident evidence, and provider errors. Copied diagnostics use the same privacy boundary and sanitize unrelated error text.

Settings

Machine Overview is enabled by default and uses the [MachineOverview] section in settings.ini next to ActiveAppView.exe. Set Enabled=0 to disable its panel and workers. The supported keys are Enabled, DisplayRefreshIntervalMs, PanelWidth, SystemSampleIntervalMs, ProcessSampleIntervalMs, TemperatureSampleIntervalMs, HistoryCommitIntervalMs, HistoryEnabled, RawRetentionHours, Rollup10sRetentionDays, Rollup1mRetentionDays, MaxDatabaseSizeMB, DetailedTraceEnabled, OnsetTraceEnabled, OnsetTraceBufferMB, and PerformanceRecordingDirectory. PerformanceRecordingDirectory defaults to empty and remembers the folder selected by Read recording. DisplayFrozen and FullView are deliberately not persisted. PanelWidth is saved as a logical 96-DPI width and scaled for the current monitor.
